AI Education MVP

AI-STUDY는 초·중·고 태블릿 환경에서, 수업자료 PDF를 기준으로 문제 생성, 풀이, 결과 확인, 자료 기반 재질문까지 이어지는 AI 학습 플랫폼 MVP입니다.

교사·학생·운영자 역할을 분리하고, React/Vite · Spring Boot · FastAPI를 나눠 배치해 짧은 공모전 기간 안에서도 제품 흐름과 서비스 경계를 함께 검증하려고 했습니다.

이 프로젝트에서 가장 중요하게 본 것은 “AI 기능을 많이 붙이는 것”이 아니라, 수업자료를 기준으로 학습 점검 → 결과 해석 → 보충학습이 다시 이어지는 폐루프를 만드는 일이었습니다. 공모전 MVP였기 때문에 운영 기능을 넓게 확장하기보다, 학교 현장에서 먼저 체감할 수 있는 교사·학생 핵심 흐름을 우선적으로 닫았습니다.

Role

개인 프로젝트 · 기획 / 프론트 / 백엔드 / AI 연동

Goal

학교 보급 태블릿 환경에서 바로 시연 가능한 교육 AI MVP 구현

Stack

React + Vite + TypeScript / Spring Boot / FastAPI / PostgreSQL

Deploy

Frontend Vercel · Backend / AI Railway 기준 설계

어떤 사용 환경을 상정했는가

이 프로젝트는 일반 웹 학습 플랫폼이 아니라, 학교에서 이미 보급된 태블릿으로 수업자료를 보며 바로 학습 흐름에 들어가는 상황을 상정했습니다.

핵심 전제는 학생이 별도 학습 툴을 새로 배우는 것이 아니라, 수업 중 보던 자료를 그대로 기준으로 문제를 풀고 모르는 내용을 다시 질문할 수 있어야 한다는 점이었습니다. 그래서 자료 열람, 문제 풀이, 결과 확인, AI 질문을 서로 다른 서비스가 아니라 하나의 문서 중심 흐름 안에 배치하려고 했습니다.

Why this matters

태블릿 보급 환경에서는 기능 수가 많기보다, 입력 부담이 적고 현재 보고 있는 자료 맥락을 잃지 않는 흐름이 더 중요하다고 봤습니다. AI-STUDY는 이 점에서 “문서 중심 학습 보조 도구”에 가깝게 설계했습니다.

왜 이 문제를 풀었는가

문제를 단순 “AI 챗봇 추가”가 아니라, 디지털 수업자료가 실제 수업 안에서 제대로 활용되지 못하는 흐름의 단절로 정의했습니다.

학생은 자료를 보다가 막히는 개념이 생겨도 바로 확인하기 어렵고, 교사는 같은 자료를 기준으로 형성평가용 문항을 만들고 학생 이해도를 점검하는 데 시간을 씁니다. 기존 도구는 자료 열람, 질문, 문제 풀이가 분리되어 있어 수업 흐름 안에서 자연스럽게 이어지지 못하는 경우가 많았습니다.

AI-STUDY는 자료 업로드 → 문제 생성 → 풀이/채점 → 결과 확인 → 자료 기반 재질문을 하나의 제품 흐름으로 묶어, “평가가 끝나면 학습도 끝나는 구조”가 아니라 “결과가 다시 학습으로 이어지는 구조”를 만드는 데 초점을 맞췄습니다.

핵심 사용자 흐름

교사, 학생, 운영자의 책임을 분리하고, 각각이 같은 자료를 다른 목적에서 다루도록 설계했습니다.

Teacher
  • PDF 수업자료 업로드
  • AI 문제 생성
  • 문항 검토 / 수정
  • 배포 코드 발급
  • 학생 결과와 취약 개념 확인
Student
  • 배포 코드로 문제 세트 입장
  • 객관식 풀이 및 제출
  • 점수 / 해설 확인
  • 오답 기반 AI follow-up 질문
  • 자료를 다시 보며 보충학습
Operator

운영자는 학교 범위 overview와 가입 승인 흐름을 담당합니다. 현재 shipped UX는 overview와 승인에 집중하고, 학교/학급/사용자 관리 capability는 백엔드에 남겨 둔 상태로 범위를 통제했습니다.

학교 범위 진입을 어떻게 다뤘는가

학생 로그인을 일반 계정 체계와 분리하고, 학교 범위 안에서만 식별과 접근이 일어나도록 설계했습니다.

학생 로그인 분리

학생은 일반 교직원 로그인과 다른 경로를 사용합니다. schoolId + studentCode + PIN 조합으로 진입하게 해, 학교 범위 안에서만 계정 식별이 이루어지도록 했습니다.

학교 검색 및 동기화

프론트에는 학교 검색 입력 흐름이 있고, 백엔드에는 학교 마스터 동기화와 학교 범위 정책이 별도로 존재합니다. 즉, 학교 선택 자체를 제품의 핵심 진입 조건으로 본 구조입니다.

시스템 구조

짧은 공모전 MVP였지만 프론트, 백엔드, AI 서비스를 분리해 책임 경계를 명확히 두었습니다.

Frontend

React + Vite + TypeScript. 교사/학생/운영자 라우트, 문서 중심 workspace, 문제 풀이와 결과 화면, QA 진입 흐름을 담당합니다.

Backend

Spring Boot. 인증/권한, 자료, 문제 세트, 제출, 결과, 대시보드, QA 로그, 학교 단위 스코프를 담당합니다.

AI Service

FastAPI 기반 별도 서비스로 PDF 분석, 문제 생성, 자료 기반 QA를 분리했습니다. 백엔드는 APP_AI_BASE_URL을 통해 외부 AI 서비스를 호출하고, 프론트는 백엔드 API만 바라보도록 구성했습니다.

핵심 설계 및 구현 포인트

기능 나열보다, 어떤 기준으로 제품을 잘랐고 어떤 리스크를 먼저 통제했는지에 초점을 맞췄습니다.

1. 학교 단위 논리 멀티테넌시

MVP 단계에서 과한 인프라 복잡도를 가져가기보다, schoolId 기반 논리적 분리와 권한 스코프 검증으로 필요한 수준의 학교 범위 분리를 먼저 적용했습니다. 즉, 물리 분리보다 적재적소의 논리 분리에 집중했고, 자료·문제세트·제출·질의응답 로그 전반에서 school scope를 반복 검증합니다.

2. 역할 기반 진입과 UX 분리

교사/학생/운영자 라우트를 분리하고, 각 역할이 보는 홈과 작업 흐름을 다르게 구성했습니다. 동일한 자료를 기준으로 하되 목적은 다르게 설계했습니다.

3. 자료 범위 밖 질문 차단

학생 AI를 자유대화형 챗봇으로 열지 않고, 현재 학습 자료 범위 안에서만 답하도록 제한했습니다. out-of-domain 질문에 대한 fallback 응답과 근거 부족 상태를 테스트로 분리해, “자료 기반 학습 도우미”라는 제품 성격을 유지하려고 했습니다.

4. 결과 이후 보충학습 연결

단순 자동채점에서 끝내지 않고, 결과 확인 화면이 오답 기반 follow-up 질문으로 이어지도록 설계했습니다. 평가가 종료점이 아니라 재학습의 시작점이 되도록 본 것입니다.

기술 선택과 트레이드오프

목표는 “완전한 교육 운영 시스템”이 아니라, 일주일 단위 공모전 안에서 핵심 가치가 전달되는 제품 흐름을 실제로 ship하는 것이었습니다.

  • React + Vite + TypeScript로 빠르게 역할별 화면과 문서 중심 workspace를 구현했습니다.
  • Spring Boot + PostgreSQL로 인증, 권한, 제출, 대시보드, 학교 스코프를 분리했습니다.
  • FastAPI + LangChain 계열 라이브러리로 PDF 분석, 문제 생성, 자료 기반 QA를 별도 서비스로 분리했습니다.
  • Railway / Vercel 기준 문서와 런북을 두어, 단순 로컬 데모가 아니라 배포 가능한 구조를 남겼습니다.
  • 운영 기능을 과하게 넓히지 않고, 원하는 서비스를 무리 없이 제공하는 데 필요한 범위에 집중했습니다.
  • 기능을 많이 보여주기보다, 역할별 플로우와 시스템 경계가 실제로 닫혀 있는지를 설명하는 방향으로 정리했습니다.

포트폴리오에서 특히 보여줄 만한 점

단기간 MVP지만, 단순 데모보다 제품형 프로젝트에 가깝게 설명할 수 있는 근거가 있습니다.

  • PRD의 핵심 플로우가 프론트 라우트, 백엔드 API, AI 서비스까지 실제로 이어지는지 별도 문서로 역검증했습니다.
  • 학교 범위 스코프, 학생 전용 로그인, QA 로그 저장처럼 교육 도메인에서 필요한 제약을 얇게나마 제품에 반영했습니다.
  • 문서 중심 workspace를 기준으로 문제 생성, 풀이, 결과, 재질문을 한 흐름에 두어 학습 맥락이 끊기지 않도록 설계했습니다.

검증 포인트와 실제 근거

설명을 뒷받침하는 코드/문서 기준 근거를 함께 정리했습니다.

확인된 제품 흐름

교사/학생/운영자 시연 흐름, 데모 계정, 권장 체험 순서가 별도 사용설명서로 정리되어 있어 단순 시안이 아니라 시연 가능한 MVP 상태를 가집니다.

검증된 QA 제한

자료와 무관한 질문에 대해 “현재 올려주신 학습 자료 범위 안에서 답변”하도록 fallback 테스트가 존재합니다.

실배포 고려

Frontend Vercel, Backend/AI Railway, PostgreSQL, R2, CORS, seed 계정, health check, release gate 문서까지 운영 관점의 흔적이 남아 있습니다.

문서와 코드의 연결

기능명세, 데이터명세, API 명세, 역할별 플로우 맵, 시스템 경계 문서가 각각 존재해 프로젝트의 판단 근거를 추적할 수 있습니다.

한계와 다음 단계

MVP였기 때문에 의도적으로 남겨 둔 부분과 실제로 보완이 필요한 부분을 구분해서 보는 것이 중요합니다.

  • 운영자 UX는 overview / 가입 승인 중심으로 얇게 노출되어 있고, latent capability 전체를 아직 프론트에 다 드러내지 않았습니다.
  • 문서 일부와 수동 QA 문서가 실제 current 상태와 드리프트가 있어 정렬이 필요합니다.
  • 프론트 테스트 하네스는 잔여 실패 케이스가 있어 안정화가 더 필요합니다.
  • 다음 웨이브에서는 operator 지표 확장, 증거 캡처 보강, 시스템 다이어그램 정리, latent API 노출 여부 결정을 진행할 수 있습니다.

이 프로젝트를 통해 보여주고 싶은 점

AI 기능을 얹는 것보다, 제품의 흐름과 책임을 어떻게 나눴는지 보여주는 쪽에 더 무게를 두었습니다.

AI-STUDY는 “AI를 붙였다”보다 학교 보급 태블릿 환경에서 실제로 쓸 수 있는 학습 흐름을 어떤 경계로 설계하고, 어떤 범위까지를 MVP로 인정할지 판단한 프로젝트에 가깝습니다. 특히 학교 단위 스코프, 역할 기반 라우팅, 자료 기반 QA 제한, 결과 이후 보충학습 연결 같은 요소는 짧은 기간 안에서도 우선순위를 나눠 제품을 만드는 방식을 보여줍니다.
