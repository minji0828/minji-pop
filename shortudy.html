숏터디 백엔드 포트폴리오

짧은 학습 영상을 업로드하고 소비하는 숏폼형 학습 플랫폼에서, 업로드·조회·운영 지표의 기준을 백엔드에서 정리한 팀 프로젝트 기록입니다. 숏터디는 사용자가 학습 영상을 업로드하고, 다른 사용자가 공개된 숏츠를 목록·카테고리·인기순으로 조회하는 서비스입니다. 저는 이 프로젝트에서 업로드 파이프라인, 상태 분리, 조회수 집계, 읽기 경로 정리, BackOffice 운영 지표 기준에 가까운 영역을 맡았습니다. 이 문서는 기능 소개보다 서비스 운영에 필요한 기준을 백엔드에서 어떻게 나눴는지에 초점을 맞췄습니다.

정리 기준

실제 구현과 화면에서 확인되는 내용만 담았고, 확인이 어려운 수치나 추정은 넣지 않았습니다.

Project Overview

기능을 더 붙이기보다, 운영 가능한 학습 플랫폼 구조를 먼저 닫았습니다.

무엇을 만들었는지보다, 어떤 문제를 어떤 기준으로 나눠 해결했는지에 초점을 맞췄습니다.

숏터디는 짧은 학습 영상을 가볍게 소비하는 서비스였지만, 제가 맡은 핵심은 화면 자체보다 업로드·검수·노출·조회·운영 숫자가 서로 충돌하지 않도록 만드는 서버 구조에 가까웠습니다. 그래서 업로드는 단순 파일 전송이 아니라 상태 관리 문제로, 조회수는 실시간 카운터보다 데이터 성격에 맞는 집계 문제로, 운영 지표는 화면 렌더링보다 숫자 해석 기준을 고정하는 문제로 정의했습니다.

대표 프로젝트 요약
  • 핵심 문제는 기능 부족보다, 업로드 완료·검수 결과·공개 여부·조회 집계·운영 지표가 하나의 흐름으로 연결되지 않으면 서비스 기준이 흔들린다는 점이었습니다.
  • 우선순위는 추천 고도화보다 업로드 파이프라인, 공개 조건, unique view, 읽기 경로, BackOffice 지표 계산 기준을 먼저 닫는 데 있었습니다.
  • 백엔드는 Presigned URL 발급, UploadSession 수명주기 관리, 공개 노출 조건, Redis write-back 집계, Query Service 기반 조회, 운영자용 집계 API를 맡았습니다.

Problem Definition

초기 우선순위는 기능 확장이 아니라 콘텐츠 품질과 운영 기준을 지키는 일이었습니다.

문제를 “기능이 더 필요하다”가 아니라, 업로드와 공개 노출, 검수, 조회 집계, 운영 지표가 서로 다른 책임인데 한 흐름처럼 다뤄지면 서비스 기준이 쉽게 흐려진다는 점으로 정의했습니다.

문제 상황

숏터디는 짧고 가볍게 소비되는 학습 경험을 지향했지만, 서비스 내부에서는 파일 업로드 완료와 실제 공개 가능 상태, 조회수 증가와 최종 반영 수치, 운영 화면 숫자와 계산 기준이 각각 다른 문제였습니다. 이 경계를 먼저 나누지 않으면, 사용자가 공개를 눌렀다는 이유만으로 바로 노출되거나, 같은 지표를 화면마다 다른 방식으로 해석하는 문제가 생길 수 있었습니다.

그래서 확장 기능보다 먼저 업로드 수명주기, 검수/공개 조건, unique view 정책, 읽기 경로, 운영 지표 기준을 서버 쪽에서 먼저 잡는 것이 우선이었습니다.

AS-IS
  • 업로드 완료와 공개 가능 상태가 섞이면 노출 정책이 불명확해질 수 있음
  • 조회 요청마다 DB를 직접 update하면 쓰기 부담이 커질 수 있음
  • 목록 조회에서 키워드와 실시간 조회수를 함께 조합하면 읽기 경로가 쉽게 비대해짐
  • 운영 지표를 화면별 임의 계산에 맡기면 숫자 해석 기준이 흔들릴 수 있음
TO-BE
  • UploadSession으로 업로드 수명주기를 별도로 관리
  • 게시 상태와 공개 설정을 분리해 노출 조건을 명시
  • Redis write-back과 24시간 unique view로 조회수 반영 전략을 분리
  • Projection + Query Service + BackOffice API로 읽기 기준과 운영 기준을 각각 고정

우선순위 정의

초기에는 추천 시스템 고도화, 문제 생성, 뱃지 같은 확장 아이디어도 있었지만, 문서와 레퍼런스 이미지 모두 학습 영상의 품질을 일정 수준 이상 유지하는 구조를 먼저 두고 있었습니다.

그래서 업로드 직후의 상태, AI 검수 결과 반영, 운영자 2차 검토 가능성, 공개 여부, 목록 조회 조건, 운영 지표 계산 기준을 먼저 닫는 쪽으로 범위를 제한했습니다.

System Architecture

백엔드는 업로드, 게시, 조회, 운영 숫자의 책임을 나누는 기준 서버에 가까웠습니다.

단순 조회 서버보다, 각 상태와 수치를 어떤 기준으로 해석할지 정리하는 서버로 설계했습니다.

백엔드의 역할: 경계와 기준 분리

숏터디 백엔드는 파일을 직접 중계하기보다, 업로드 시작과 완료를 어떻게 해석할지, 어떤 숏츠가 사용자에게 보여도 되는지, 조회수를 어떤 단위로 반영할지, 운영 지표를 어떤 기간 기준으로 계산할지를 결정하는 역할에 가까웠습니다.

  • 업로드는 Presigned URL 발급과 UploadSession 상태 관리로 분리
  • 콘텐츠 노출은 Upload Status와 Visibility를 함께 만족하는 조건으로 해석
  • 목록 조회는 Projection 기반 기본 조회, 키워드 배치 조회, Redis pending count 병합으로 분리
  • 운영 지표는 사용자 서비스와 별도 BackOffice API에서 KST 기준으로 계산
전체 시스템 구조

Client / BackOffice → Spring Boot API → MySQL(RDS) / Redis / AWS S3

핵심 구조 의도

업로드 수명주기, 노출 정책, 조회 집계, 운영 숫자를 각각 다른 책임으로 나누고, 수정 지점을 명확하게 유지하려고 했습니다.

역할 분리 포인트

UploadSession은 업로드 수명주기, Shorts는 게시 콘텐츠, Query Service는 읽기 조립, BackOffice는 운영자용 계산 기준을 맡도록 역할을 나눴습니다.

Case Studies

핵심 설계 및 구현

핵심 설계는 실제로 문제를 나눠 풀었던 기준을 따라 정리했습니다.

1. S3 Direct Upload와 UploadSession으로 업로드 수명주기를 분리

문제는 direct upload가 서버 부하를 줄여 주는 대신, 중단·재시도·만료·고아 데이터 같은 불완전 상태를 자연스럽게 만들어 낸다는 점이었습니다.

결정

Presigned URL 발급을 기준으로 업로드를 시작하고, 별도의 UploadSession으로 사용자·파일 메타데이터·만료 시간·완료 여부를 관리했습니다.

이유

Multipart Upload는 숏폼 영상 크기 기준에서 이점이 크지 않았고, STS는 초기 프로젝트에 비해 권한 설계와 클라이언트 복잡도가 과하다고 봤습니다. Presigned POST도 URL 대비 분명한 이점을 크게 느끼지 못해 구현 속도, 백엔드 부하 최소화, 구조 단순성을 기준으로 Presigned URL을 택했습니다.

한계

현재 구조는 complete 요청을 일부 신뢰하므로, 실제 S3 객체 존재를 서버가 100% 보장하지는 못합니다. 후속으로는 S3 이벤트 기반 검증이나 더 강한 완료 확인이 필요합니다.

Client → Backend → AWS S3 → UploadSession DB 흐름을 직접 정리한 시퀀스 다이어그램입니다. 업로드 시작 요청, Presigned URL 반환, S3 direct upload, complete 요청, 세션 검증과 만료 세션 정리까지 업로드 수명주기를 별도 세션으로 관리했다는 근거를 보여줍니다.

2. 업로드 상태와 공개 상태를 분리해 노출 조건을 명시

문제는 파일 업로드 완료가 곧바로 사용자 노출 가능 상태를 의미하지 않는 서비스였다는 점입니다. 실제 운영 흐름에서도 검수 대기, AI 점검, 게시, 반려를 서로 다른 상태로 다뤄야 했습니다.

결정

업로드 완료와 게시 가능 상태를 같은 값으로 보지 않고, 조회 시에는 Upload Status = PUBLISHED와 Visibility = PUBLIC을 함께 만족할 때만 노출되도록 했습니다.

이유

사용자의 공개 의사, AI 검수 결과, 운영자 2차 검토 가능성은 서로 다른 책임이기 때문에 하나의 상태로 합치면 정책 변경 지점이 흐려집니다. 상태와 조회 조건에 정책을 나눠 두는 편이 운영 흐름을 다루기 쉬웠습니다.

한계

상태가 늘수록 조회 쿼리와 테스트 기준도 더 엄격하게 유지해야 합니다. 대신 검수 흐름과 노출 정책을 별도로 바꾸기 쉬운 구조를 확보할 수 있습니다.

운영 화면에서도 검수 대기, AI 점검, 게시, 반려를 분리해 다룬다는 점을 보여 주는 영상 검수 대시보드입니다. 공개 여부를 하나의 불리언으로 처리하지 않고, 검수 상태와 운영자 액션을 별도 단계로 관리했다는 근거로 배치했습니다.

3. 조회수는 Redis write-back과 24시간 unique view 기준으로 집계

문제는 조회수를 결제 데이터처럼 즉시 정합성 중심으로 다루기보다, 잦은 쓰기와 중복 조회를 함께 다루는 방식이 더 중요했다는 점입니다.

결정

Redis INCR로 조회수를 먼저 누적하고, 스케줄러가 주기적으로 MySQL에 flush하는 write-back 구조를 적용했습니다. unique view는 24시간 기준으로, 로그인 사용자는 사용자 ID, 비로그인은 IP + User-Agent 해시 기준으로 집계했습니다.

이유

조회수는 약간의 반영 지연보다 서비스 가용성과 쓰기 부하 분산이 더 중요한 데이터였습니다. 당시에는 로컬 캐시, 메시지 큐, 로그 집계 같은 대안도 있었지만, 프로젝트 단계와 운영 복잡도를 함께 보면 Redis가 가장 현실적인 선택이었습니다.

한계

비로그인 식별에 IP + User-Agent 해시를 쓰는 방식은 정책적으로 더 신중해야 했고, 회고 기준으로는 서버 발급 익명 UUID 쿠키가 더 적절하다고 봤습니다. 또한 당시에는 속도를 우선해 일부 내구성 손실 가능성을 감수한 설정도 함께 검토했습니다.

조회수 증가 처리와 flush 로직을 한 화면에서 보여 주는 서비스 코드입니다. `markUniqueView`로 중복 조회를 거른 뒤 `increaseViewCount`로 Redis 누적값을 올리고, 이후 `findPendingViewCounts` → `updateViewCount` → `clearPending` 순서로 DB에 반영하는 흐름이 보입니다.

4. Projection + Query Service로 읽기 경로를 단순화

문제는 숏츠 목록 응답이 기본 정보 외에도 키워드와 실시간 조회수를 함께 조합해야 해, 읽기 경로가 쉽게 무거워질 수 있었다는 점입니다.

결정

기본 응답은 Projection 기반으로 조회하고, 키워드는 배치 조회로 채우며, Redis pending 값은 Query Service에서 병합하도록 나눴습니다.

이유

초기에는 Facade처럼 조회 책임을 감싸는 방향도 검토했지만, 이 문제의 핵심은 패턴 이름보다 필요한 데이터를 적절한 쿼리로 가져오고 N+1을 줄이는 데 있었습니다. 그래서 읽기 전용 책임만 얇게 분리하는 쪽을 택했습니다.

한계

기본 조회, 키워드 로딩, 실시간 카운트 병합이 분리되면서 읽기 흐름을 문서와 테스트로 계속 보강해야 합니다. 대신 응답 조립의 수정 지점을 더 분명하게 유지할 수 있습니다.

5. BackOffice 지표는 숫자 해석 기준을 서버에서 고정

문제는 운영 지표가 단순 조회가 아니라, 기간 계산·분모/분자 기준·반올림 규칙이 조금만 달라도 다른 숫자가 나오는 영역이었다는 점입니다.

결정

BackOffice API에서 게시 추세와 전환율을 계산하고, 기간 계산은 KST 기준으로 고정했으며, 전환율은 같은 기간에 생성된 전체 숏츠 대비 게시 완료 수 기준으로 계산했습니다. 입력 기간 제한과 반올림 규칙도 서버에서 명시했습니다.

이유

운영 숫자를 화면마다 임의 계산하게 두면 같은 서비스 안에서도 기준이 달라질 수 있습니다. 그래서 운영 화면은 데이터를 그리는 UI보다 서버가 기준을 보장하는 관리 도구에 가깝게 두었습니다.

한계

현재 구조는 DB에서 바로 수집 가능한 지표 중심의 Phase 1에 가깝습니다. 이후 더 세밀한 운영 지표를 보려면 백엔드 로그와 프론트 이벤트 수집까지 함께 확장해야 합니다.

Shortudy Admin 대시보드의 운영 지표 화면입니다. 가입자 수, 일일 업로드 수, 게시 전환율, 카테고리 분포처럼 BackOffice 기준이 실제로 어떤 화면에서 쓰이는지 보여 줍니다.

Trade-offs

기술 선택과 트레이드오프

숏터디에서는 “어떤 기술을 썼는가”보다, 왜 지금 그 기술이 문제의 크기와 운영 비용에 맞았는지를 설명하는 쪽이 더 중요했습니다.

Presigned URL direct upload

서버 부하를 줄이고 구현 속도를 확보하기에는 적절했지만, 객체 존재 검증과 후처리 설계는 별도 보완이 필요합니다. 대용량 파일이 주 흐름이 아니라는 점이 선택의 배경이었습니다.

Redis write-back

조회수의 데이터 성격상 즉시 정합성보다 부하 분산이 중요하다고 봤지만, flush 전 일시 불일치와 guest 식별 한계는 감수한 구조였습니다.

상태 분리와 조회 조건 명시

정책 변경 지점은 선명해지지만, 상태 수와 테스트 기준이 함께 늘어납니다. 그래도 업로드 성공과 공개 가능 상태를 분리해 두는 편이 운영하기 쉬웠습니다.

BackOffice 단계적 확장

모든 운영 지표를 한 번에 만들기보다, 현재 DB에서 바로 계산 가능한 지표부터 Phase 1로 두고 이후 로그·이벤트 수집과 함께 넓히는 방식을 택했습니다.

추가 설계 메모

썸네일 자동 생성도 direct upload의 장점을 해치지 않도록 업로드 본 처리와 분리해 두는 쪽을 생각했습니다. 초기에는 Lambda 기반 이벤트 처리, 이후 규모가 커지면 SQS 완충과 MediaConvert 리팩터링까지 검토했습니다.

Operations

운영, 검증 그리고 향후 계획

구현 자체보다, 실패 가능한 경로와 기준이 어디에 남아 있는지가 더 중요하다고 생각했습니다.

운영을 위한 기준

만료 세션 / 고아 데이터 정리

재시도 시 기존 미완료 세션을 정리하고, 스케줄러로 오래된 업로드 세션과 잔여 데이터를 주기적으로 정리했습니다.

삭제 무결성 처리

`shorts_like` 같은 자식 row가 FK를 잡는 경우를 서비스 레벨에서 먼저 정리한 뒤 부모를 삭제하도록 순서를 제어했습니다.

배포 구조 재정리

초기 단일 EC2 구성을 운영하며 한계를 확인한 뒤, DB를 RDS로 분리하고 서비스 구성요소를 나누는 방향으로 수정했습니다.

한계 및 향후 계획

이 페이지에는 확인 가능한 내용만 담았고, 응답 속도 개선율이나 트래픽 규모 같은 정량 성과는 넣지 않았습니다.

또한 CI/CD, 관측성, 보안 전반은 당시 충분히 깊게 다루지 못했습니다. 이후에는 S3 객체 존재 검증 강화, guest 식별 방식 개선, 로그·이벤트 수집 보강이 필요합니다.

보여주고 싶은 역량
  • 파일 업로드를 단순 전송 기능이 아니라 상태 관리 문제로 바꾸어 보는 능력
  • 업로드 성공, 노출 정책, 조회 집계, 운영 숫자를 서로 다른 책임으로 나누는 모델링 능력
  • 조회수처럼 데이터 성격이 다른 값을 정합성과 부하 분산 관점에서 설계하는 능력
  • Projection, 배치 조회, Query Service로 읽기 경로를 단순화하는 판단
  • 운영 화면 숫자도 결국 서버 기준이 고정되어야 의미가 생긴다고 보는 관점
  • 팀 프로젝트에서도 확인 가능한 범위만 말하고, 한계와 후속 과제를 함께 남기는 문서화 태도
